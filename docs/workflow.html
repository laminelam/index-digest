How Hierarchical Index Digest Verifies an Index

A background scanner turns each shard into a tree of frozen fingerprints, so two indices can be compared in milliseconds instead of a full scan — and the exact range where they disagree can be pinpointed in a handful of probes.

The idea in one picture

Why old work never gets redone

Every document carries an external version field — by default version_ts — whose value the producer increases with every write. That number, not time or insertion order, is the axis the tree is built on. Documents are grouped into fixed ranges of it, and once the newest data has moved far enough past a range, that range is sealed: hashed once, stored, never revisited.

What happens on every scan tick

The pipeline, in order — each step gates the next

A scheduler fires on UTC wall-clock boundaries, so independent clusters seal at nearly the same moments. Each tick runs one shard copy at a time, and the ordering is the safety mechanism: nothing advances a watermark until the work it covers is durably recorded.

Comparing two indices

Equal subtrees are skipped whole

Comparison never reads documents. It reads digests, top-down: if two nodes match, everything beneath them matches and is skipped; if they differ, the search descends into the differing child only. A divergence anywhere in a billion-document index is found in a handful of round trips.

Deletes, without breaking immutability

The problem the RFC left open

A delete removes a document and leaves nothing on the version axis — so a delete that reached one cluster and not the other would be invisible to both trees. The fix uses what OpenSearch already writes: every delete leaves a tombstone carrying the doc's id and the external version supplied with the delete. The scanner reads those, turns them into durable events, and folds them into the digest of the window they belong to — a new window, never the old one.

When timing plays tricks

Detect, repair, and tell the two apart

Two clusters seal the same window at slightly different moments. If a delete lands between those moments, one side sealed the window with the document and the other without it — identical data, different digests. The tool cannot prevent this (the delay is replication lag, not something the scanner controls), so instead it repairs it, and uses the repair itself to distinguish a timing artifact from real divergence.

The overhead figure is a deliberate worst case: the scanner was sealing continuously on a single node that was simultaneously absorbing bulk ingest. At a production cadence — a tick every few minutes, sealing a small increment — the duty cycle is a fraction of a percent.

What it does not do. Content is not hashed: the tree assumes a document's external version changes whenever its contents change. Deletes must be issued with an external version. Replica-to-replica comparison is supported only when writes are quiesced. These are stated boundaries, not gaps discovered later — the tool reports honestly inside them and fails loudly outside them.
